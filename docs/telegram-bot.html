Stazione Meteo — Telegram Bot Reference

Incoming commands and outgoing Telegram API payloads served by the alarm watcher.

Source of truth: rapsberry meteo/alarm_watcher.py  ·  Command menu registered on startup via setMyCommands  ·  Long-polling loop (getUpdates) for inbound commands.

1Supported commands inbound

Parsed by handle_command(). A trailing @botname (added by Telegram in groups) is stripped before matching. Unknown commands are silently ignored. Only messages from the configured CHAT_ID are processed — anything else is logged and dropped.

Command Handler Reply
/start
/help		 HELP_TEXT Static list of available commands.
/status format_status() Latest reading for every sensor (Full Sun, Ombra, Interno, Potenza, CPU…), fan state and station id.
/forecast format_forecast() Clear-sky 6 AM temperature forecast (radiative cooling, floored at dew point) per outdoor sensor.
/alarms format_alarms_summary() All configured rules, their conditions, target bot, and which are currently firing.
/reboot do_reboot() Confirms, then reboots the Raspberry after a 3 s delay (needs a NOPASSWD sudoers entry).
Menu vs. handlers. The menu (the blue “/” list in the chat) is registered separately from the handlers. The five menu entries are pushed to Telegram on every startup; /start works as a handler but is intentionally not listed in the menu.

2Outgoing API payloads outbound

Every call targets https://api.telegram.org/bot<TOKEN>/<method>. The default token/chat come from zbot.py (BOT_TOKEN, CHAT_ID); alarm rules may override them per-rule (see §4).

POST/sendMessage

Sends any bot message — command replies, boot notice, alarm text, reboot confirmation. Form-encoded body:

POST https://api.telegram.org/bot<TOKEN>/sendMessage
Content-Type: application/x-www-form-urlencoded
timeout: 10s

chat_id = <CHAT_ID>
text    = <message text>

POST/setMyCommands

Registers the command menu once at startup. JSON body:

POST https://api.telegram.org/bot<TOKEN>/setMyCommands
Content-Type: application/json
timeout: 10s

{
  "commands": [
    { "command": "status",   "description": "Valori correnti" },
    { "command": "forecast", "description": "Previsione 6am (cielo sereno)" },
    { "command": "alarms",   "description": "Soglie configurate e allarmi attivi" },
    { "command": "reboot",   "description": "Riavvia il Raspberry" },
    { "command": "help",     "description": "Elenco comandi" }
  ]
}

GET/getUpdates — long poll

Main loop; blocks up to TG_POLL_TIMEOUT (25 s) waiting for inbound messages.

GET https://api.telegram.org/bot<TOKEN>/getUpdates
timeout (HTTP): 35s

timeout = 25          # long-poll seconds
offset  = <last update_id + 1>

GET/getUpdates — drain at boot

Run once on startup to skip messages queued while the watcher was offline.

GET https://api.telegram.org/bot<TOKEN>/getUpdates
timeout (HTTP): 10s

timeout = 0
offset  = -1          # jump straight to the newest update

3Bot-initiated messages outbound

Fixed-text messages the bot sends without being asked (all via /sendMessage).

Trigger Message text
Watcher startup / Raspberry boot 🔌 Raspberry avviato — stazione meteo online.
/reboot accepted Riavvio del Raspberry in corso… 🔄
/reboot failed to spawn Impossibile avviare il riavvio (vedi log del watcher).
Handler raised an exception Errore interno durante l'esecuzione del comando.
Alarm rule fires Rule's configured message, or [ALARM] <description> when blank.

4Multi-bot routing outbound

Alarm rules can send through a dedicated bot instead of the default one. Bots are stored in alarms.db (bots table) and edited from alarms.php.

send_rule_message() looks up the rule's bot_id. If that bot has both a token and a chat_id, the alarm goes out on that bot/chat; otherwise it falls back to the default BOT_TOKEN / CHAT_ID. Inbound command polling always uses the default bot only.
